# TestTracks Playwright C#

This is a Windows-focused Playwright C# starter framework for browser and API test automation using .NET, NUnit and Reqnroll BDD.

It is intended as a clean project shape for testers and teams who want BDD feature files, Playwright browser automation, Playwright API testing, environment-based test data, page objects, thin API clients, cleanup, reports and evidence capture without building a full application SDK.

The repository includes a small set of example tests against `https://automationintesting.online`. The demo app is only there to make the framework concrete.

## Requirements

- Windows.
- .NET 10 SDK.
- Internet access to restore NuGet packages and install Playwright browser binaries.
- Access to the public demo application at `https://automationintesting.online`, only if you want to run the example tests.

Install the SDK with:

```powershell
winget install Microsoft.DotNet.SDK.10
```

Confirm the SDK is available:

```powershell
dotnet --list-sdks
```

You should see a `10.0.xxx` SDK.

Run the rest of the commands from the `playwright-csharp` project root in Windows PowerShell.

## Quick Start

```powershell
dotnet restore
dotnet build
& .\artifacts\bin\test-tracks-playwright-csharp.specs\Debug\net10.0\playwright.ps1 install chromium
```

Then run the tests:

```powershell
dotnet test
```

By default this runs the automatic checks, then runs the tests against `dev`, Chromium and headed browser mode.

## Install Playwright Browsers

Playwright browser binaries are installed separately from NuGet packages. Run `dotnet build`, then run the generated `playwright.ps1` script from the build output.

Install Chromium:

```powershell
& .\artifacts\bin\test-tracks-playwright-csharp.specs\Debug\net10.0\playwright.ps1 install chromium
```

Install Firefox:

```powershell
& .\artifacts\bin\test-tracks-playwright-csharp.specs\Debug\net10.0\playwright.ps1 install firefox
```

Install Microsoft Edge:

```powershell
& .\artifacts\bin\test-tracks-playwright-csharp.specs\Debug\net10.0\playwright.ps1 install msedge
```

The script above is generated by Playwright during build. It is not a custom project script, and there is no `scripts` folder in this repository.

Re-run the relevant install command after updating the Playwright NuGet package, because Playwright versions expect matching browser binaries.

## Quality Checks

`dotnet test` automatically runs:

- restore, unless `--no-restore` is used
- build through the C# compiler
- formatting verification through `dotnet format whitespace --verify-no-changes --no-restore`
- lint verification through `dotnet format style --verify-no-changes --no-restore`
- the matching tests

Formatting and linting are handled by the .NET SDK's `dotnet format` command and `.editorconfig`.

Run the formatting check without running tests:

```powershell
dotnet format whitespace --verify-no-changes --no-restore
```

Run the lint check without running tests:

```powershell
dotnet format style --verify-no-changes --no-restore
```

Fix formatting and lint issues:

```powershell
dotnet format --no-restore
```

## Run Options

Default runs use:

- environment: `dev`
- browser: `chromium`
- headless: `false`

Use `dotnet test -e NAME=value` to change those values for one run. This passes values into the test process only; it does not save permanent Windows environment variables.

Supported values:

```text
ENV       dev, test, or another folder under tests/Data/Environments
BROWSER   chromium, firefox, edge
HEADLESS  true, false
```

Run against the `test` environment data:

```powershell
dotnet test -e ENV=test
```

Run against the `test` environment in headless mode:

```powershell
dotnet test -e ENV=test -e HEADLESS=true
```

Run with a specific browser:

```powershell
dotnet test -e BROWSER=chromium
```

Run with Firefox:

```powershell
dotnet test -e BROWSER=firefox
```

Run with Edge:

```powershell
dotnet test -e BROWSER=edge
```

Edge uses Playwright's Chromium browser type with the `msedge` channel. If Edge is requested but unavailable, the tests fail instead of silently falling back to Chromium.

Install the matching Playwright browser before the first run. For `BROWSER=edge`, install `msedge`.

To run headed or headless:

```powershell
dotnet test -e HEADLESS=false
dotnet test -e HEADLESS=true
```

When using filters, keep `-e` values on the same command:

```powershell
dotnet test --filter "TestCategory=ui" -e ENV=test -e HEADLESS=true
```

## Environment Data

Environment data lives under:

```text
tests/Data
  Environments
    dev
    test
  DataBuilders
    RestfulBooker
```

Each environment folder has the same set of files:

```text
all-targets.json
api-auth.json
api-booking.json
api-room.json
ui-booking.json
```

`all-targets.json` contains named UI sites, named API endpoints, credentials, timeouts and trace settings for that environment. This avoids assuming there is only one UI base URL or one API base URL.

Example shape:

```json
{
  "sites": {
    "restfulBooker": {
      "baseUrl": "https://automationintesting.online"
    }
  },
  "apis": {
    "restfulBookerApi": {
      "baseUrl": "https://automationintesting.online/api/"
    }
  }
}
```

There are no default site, API or credential entries. Step definitions explicitly request the named site, API and credential they need.

The other files contain data for the matching example tests: payloads, expected values, boundary values, date offsets, selection criteria and other test variations. They should not contain environment wiring such as API target names, site target names or setup credential names.

API request payloads should usually start in these JSON files too. Data builders can clone that base payload and override fields for uniqueness, boundaries, missing fields or negative cases before sending it.

Admin credentials used only for setup come from `all-targets.json`. Credentials being tested, such as valid or invalid login payloads, belong in the scenario data because those values are the subject of the test.

The JSON loader can read a whole file or a named subset within a file. The example tests use sections such as:

```text
ui-booking.json -> scenarios.availableRoom
ui-booking.json -> scenarios.guestCanCreateBooking
```

That lets one file hold multiple scenario data blocks while keeping data as data, configuration as configuration and step definitions responsible for how the test uses them.

To add another environment later, create a new folder such as `tests/Data/Environments/uat` with the same file names, then run:

```powershell
dotnet test -e ENV=uat
```

If the folder does not exist, the test run fails with the available environments listed.

## Reports and Evidence

Each test run writes evidence to its own timestamped folder under:

```text
TestResults/20260820-125641/
```

That folder contains the Reqnroll HTML report and Cucumber Messages. The report shows run details, including environment, browser and headless mode. API evidence is written into the report. Browser console output and page errors are added only when something is captured. UI failures also include a screenshot and zipped Playwright trace.

## Structure

```text
src
  generic Playwright API & UI, runtime, cleanup, configuration and diagnostics code

tests
  Features
  Steps
  Pages
  Data
  Configuration
  Reporting
  Support

artifacts
  build output only
```

`src` contains reusable test framework code. `tests` contains the BDD features, step definitions, page objects, environment data, builders, reporting hooks and demo-specific example code.

## Framework Responsibilities

**Environment = where. Data = what. Builders = make it usable/unique. Steps = intent and orchestration. Supporting test code = application knowledge. Base classes = Playwright plumbing.**

- **Environment** - URLs, named targets, credentials and framework settings.
- **Data** - scenario payloads, expected values, boundary values and negative values.
- **Builders** - clone or modify data, add uniqueness and make scenario-owned resources.
- **Steps** - describe test intent and orchestrate the scenario.
- **Supporting test code** - owns endpoint paths, page locators, auth/application quirks and domain-specific calls.
- **Base classes** - generic Playwright browser/API mechanics, evidence, redaction and transport.

Scenario data should not contain framework wiring, and step or supporting test code should not contain environment URLs or credentials directly.

## How It Works

Each scenario gets its own state object. API scenarios create named Playwright API request contexts as needed; UI scenarios also get a fresh browser, browser context and page. No browser context is shared between scenarios.

Mutable data is owned by the scenario that creates it. Cleanup is registered immediately after data is created and runs after the scenario, even when the scenario fails.

Page objects expose user-facing behaviour and keep locators inside the page class. API clients keep endpoint paths, auth quirks and service behaviour out of the feature files and step definitions. Generic HTTP mechanics live in `BaseApi`.

## Example Scope

The Auth, Room and Booking services are included as examples of how to organise a real project across API, UI, data, cleanup and BDD layers.

When adapting this repository to another application, keep the framework foundations and replace the demo-specific examples:

- Keep `Configuration`, `Runtime`, `Cleanup` and `Diagnostics` unless your project has a better equivalent.
- Keep `API/Common/BaseApi.cs` and `UI/Common/BasePage.cs` as thin starting points.
- Replace or remove `tests/Steps/RestfulBooker/API/Auth`, `Room` and `Booking` when those API clients do not exist in your application.
- Replace or remove `tests/Pages/RestfulBooker/Admin` and `Booking` when the demo UI is no longer the target.
- Replace the feature files under `tests/Features/RestfulBooker` and step definitions under `tests/Steps/RestfulBooker` with behaviour for your own application.
- Keep the environment JSON, test data and cleanup pattern, but change the builders under `tests/Data/DataBuilders/RestfulBooker` to create your application's own mutable data.

The example tests are intentionally small. They are there for understanding only: structure, scenario ownership, API setup, UI interaction and reporting evidence.

## Adding Coverage

For a new API area, add payload data under `tests/Data/Environments`, add data builders under `tests/Data/DataBuilders/<service>`, and add thin API clients under `tests/Steps/<service>/API/<area>`. Keep request payloads flexible by default; keep small response records beside the API client only where they make assertions, cleanup or reusable state clearer.

For a new UI area, add app-specific page objects under `tests/Pages/<service>`, keep locators in the page object, and consume those page objects from step definitions under `tests/Steps/<service>/UI`. Feature files should describe behaviour, not selectors, route paths or Playwright mechanics.

## Design Rules

- No Selenium-like wrapper around Playwright.
- No mutable state shared between scenarios.
- No fixed sleeps for browser synchronisation.
- API setup is used for UI prerequisites where useful.
- API request payloads are test data first; avoid building a full application SDK.
- Cleanup is registered immediately after mutable data is created.
- Secrets are redacted before evidence is written.
- No Allure, ExtentReports, SpecFlow, Selenium, RestSharp or external DI framework.

For page objects, keep stable text/selectors near the top of the class, put locator properties or factories before the constructor, prefer role/label/test-id locators, and keep any necessary fallbacks narrow and named.
